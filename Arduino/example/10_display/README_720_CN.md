# 4.0 寸 720×720 屏幕适配

依据参考资料目录中的 `0400A008-T1I1000  中英文规格书 2025-11-12.pdf` 和
`BOE4.0_IPS(AV040YNU-N80-1QP01QP1)_JD9365D-H3_720x720_7721_4L_Column.txt`。

## 编译错误原因

`PanelRegister` 只有两个字段：`uint8_t command; uint8_t value;`。
厂家格式 `{0xE0, 1, {0x00}}` 有三个字段：命令、参数个数、参数数组，
直接粘贴会产生 `too many initializers for 'const PanelRegister'`。
本示例每条厂商寄存器写入均为单字节，因此转换为 `{0xE0, 0x00}`。
以后遇到多字节参数，必须同时扩展结构体和发送函数，不能仅删除参数个数。

## 软件配置

| 项目 | 当前设置及依据 |
| --- | --- |
| 有效分辨率 | WIDTH=720、HEIGHT=720 |
| 初始化表 | 新屏的 194 条寄存器写入；电源、Gamma、GIP 和顺序与厂家表一致 |
| DSI 通道 | ESP32-P4 使用 2 条；Page 0 的 0x80 从厂家 0x03 改为 0x01，从初始化开始就使用此值 |
| 水平时序 | HSA=20、HBP=20、HFP=40，来自厂家文件 |
| 垂直时序 | VSA=4、VBP=12、VFP=24，来自厂家文件 |
| 像素时钟 | 请求 36.48 MHz，按 (720+20+20+40)×(720+4+12+24)×60 计算；待实屏验证 |
| DSI 速率 | 保留 500 Mbps/lane；RGB565 像素负载按含消隐时钟估算约 291.84 Mbps/lane，实际还存在协议开销 |
| 像素格式 | 保留 RGB565，DPI 格式、uint16_t 帧缓冲、Page 0 的 0x3A=0x55 保持一致；需实屏验证模块支持 |
| 帧缓冲 | 单帧 1,036,800 字节，继续启用 PSRAM |
| 彩条 | x×8/WIDTH，每条 90 像素；旧 x/100 会使黑条只剩 20 像素 |
| 复位 | 保留厂家高 5 ms、低 10 ms、释放后 120 ms |
| 标准命令 | setup 单独发送 0x11，等待 120 ms；发送 0x29，等待 5 ms |
| TE | 厂家末尾 0x35 开启 TE，本例没有使用 TE，因此省略；不影响持续视频输出逻辑 |

Page 1 的 0x80=0x32 是厂家 Gamma 表的一部分，不能随 Page 0 的通道配置一起修改。
两通道值 0x01 参考本地 `Arduino/libraries/ESP32_Display_Panel/src/drivers/lcd/port/esp_lcd_jd9365.c`。
厂家 `PLL_CLOCK=219` 为原平台 DSI 参数，不能直接当作 ESP32 的 `dpi_clock_freq_mhz`，
也不能在缺少原平台时钟定义时直接当作 `lane_bit_rate_mbps`。
旧像素时钟 44.352 MHz 配上新的分辨率和相同时序，理论刷新率约 72.95 Hz。

## 上板前的硬件核对

- 规格书第 1 页（PDF 第 4 页）标注 MIPI-4L；厂家序列也是 4L。ESP32-P4 的 DSI 是两条数据通道。
  当前修改是两通道适配方案，不能仅凭寄存器设置认定该模组已支持；需厂家确认或实屏验证。
  若模组仅支持 4L，软件无法让 ESP32-P4 增加两条物理通道。
- 引脚表第 3 页（PDF 第 6 页）：4 脚为 3.3 V，21 脚 IOVCC 标称 1.8 V。
  第 4 页电气表又列 IOVCC 范围 1.65～3.6 V，需要厂家确认该模组的实际供电要求。
  若使用 1.8 V IOVCC，还需核对 RST 等控制信号的电平匹配，不能仅改电源。
- 背光标称 24 V、40 mA（8 LED）；核对 AP3032 升压能力、限流电阻和实际 LED 电流。
  GPIO33/26 控制方式取决于底板电路，不因分辨率改变而自动变化。
- GPIO27 RESET、GPIO33 BL_EN、GPIO26 BL_PWM 沿用现有底板配置。
  LDO3/2500 mV 是 ESP32-P4 MIPI PHY 的电源配置，不是屏幕 IOVCC 或背光电压。
- 此例没有触摸功能。若迁移 11/12 的 LVGL 示例，还需分别适配显示分辨率、布局、触摸驱动、地址及坐标范围。

## 固定青色、串口 Pattern 正常时的诊断

诊断版本的启动日志含 `[DSI DIAG 1]`。原有时序、速率和初始化寄存器保持不变。
重新编译烧录后，按顺序发送以下单字符，各等待几秒观察：

| 命令 | 功能 |
| --- | --- |
| t | ESP32-P4 DSI 主机硬件竖彩条，绕过 PSRAM 像素数据；暂停轮播 |
| h | 主机硬件横彩条；暂停轮播 |
| f | 恢复帧缓冲画面，保持暂停；0～6 也会退出硬件图案 |
| o | 发送面板 Display OFF（0x28），不关闭背光 |
| p | 发送面板 Display ON（0x29），不改变背光 |
| d / e | 单独关闭／开启背光，便于与 o/p 区分 |

硬件彩条是主机产生的视频数据，不是屏幕内部自检。
若 t/h 能显示并切换，视频链路至少能够显示硬件图案，继续排查帧缓冲/DMA路径。
若 t/h 也完全不变，则问题不能仅用绘图函数或缓存写回来解释，应继续检查视频链路、初始化和硬件。
若 o/p 可见地改变显示，说明面板至少响应这些控制命令；不代表视频参数正确。
若 o/p 没有可见变化，不能单凭此项断言命令链路损坏，仍需读回或硬件测量佐证。
先记录上述测试结果，再决定是否调整像素格式、时钟或初始化，避免多项同时变化。
新增诊断接口及枚举已核对 Arduino core 3.3.7 所带头文件；诊断版本尚未完整编译或上板验证。

## DIAG 2：硬件彩条正常，帧缓冲仍固定青色

用户实测 t/h 可切换，返回帧缓冲仍为固定青色，因此优先排查帧缓冲/DMA/DSI bridge。
DIAG 2 保持 36.48 MHz、500 Mbps/lane、RGB565 和初始化表不变：

- 上电只绘制静态红色，不自动轮播，避免持续写 PSRAM 干扰诊断；a 可恢复轮播。
- 初始填充后仍进行缓存写回；后续图案使用标准 esp_lcd_panel_draw_bitmap 提交驱动自己的帧缓冲。
  原来的直接写缓冲并同步缓存并非已证实的错误，此项用于统一提交路径。
- 每两秒打印刷新事件总数、增量、实际采样间隔，以及 CPU 看到的首像素。
- ESP32-P4 ECO2 的刷新回调可用于观察主机 DMA 整帧完成活动；不是面板接收确认。
  HOST_PATTERN 模式绕过帧缓冲，此时不能用计数停滞判断故障。

烧录后先不要发送 t/h，保留上电后的 6～10 秒日志，然后发送 3 再记录几秒。
红色首像素应为 F800，白色为 FFFF；计数持续增长表示主机持续产生刷新完成事件。
若计数不增长，优先检查 DMA 启动/传输/中断；若增长但仍青色，继续检查 bridge 数据路径和格式。
如出现 underrun 日志，说明驱动检测到取数不足；无该日志不能完全排除，输出还受日志级别影响。
参考本地 ESP-IDF 5.5.4 驱动含有 underrun 导致蓝屏的说明，Arduino 实际使用的 SDK 为 5.5.2，
因此该说明只是排查线索，不作为本次故障已确诊的依据。
DIAG 2 仅做了静态接口与逻辑核对，尚未完整编译或上板验证。

## DIAG 3：刷新事件始终为 0 的降速对照

DIAG 2 实测 CPU 首像素能由 F800 改为 FFFF，但刷新事件持续为 0，屏幕仍青色。
此结果未证明具体根因，需区分 DMA 停滞、错误、完成中断异常和 bridge 供数不足。
已只读核对 Arduino 3.3.7 的 libesp_lcd.a 中 dpi_panel_init：包含 DMA 链表配置和通道启动调用。

当前代码 PIXEL_CLOCK_MHZ 临时设为 24.0（理论约 39.47 Hz）；36.48 是此前目标 60 Hz 配置。
这不是厂家确认的刷新率，仅用于降低视频取数需求的对照，成功后仍需恢复目标时钟复测。
通道数、lane 速率、RGB565、分辨率和厂家寄存器保持原值。
计数无增长时自动打印两次 DMA/bridge 快照，或发送 s 手动读取。
快照读取全部 DMA 通道，不假定显示通道编号；不修改寄存器或清除中断。
raw_irq 为瞬时状态，ISR 可能已清除错误位，读到 0 不代表从未发生错误。

烧录后先不要进入硬件彩条，等待约 8 秒，发送 3，再等待几秒。
若红白能切换且计数增长，说明降速条件下帧缓冲路径可工作，优先检查带宽/时序余量。
若仍为 0，保留包含 BRIDGE、DMA、DMA0～DMA3 的日志以进一步定位；不再只重复观察颜色。
本版寄存器成员已与当前 SDK 头文件核对，尚未完整编译或实屏验证。
